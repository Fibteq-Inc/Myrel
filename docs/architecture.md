# Architecture

This page describes how Fibteq Myrel is put together today and where it is
heading. It is meant for contributors; for running Myrel, see
[self-hosting.md](self-hosting.md).

## The model

A **project** is a shared space with a **project chat**. Every message there
goes to the project's **coordinator** agent. The coordinator does no research
or work itself; it only routes:

- a new ask gets a **thread**, with a **thread agent** assigned to it;
- a follow-up goes to the thread it belongs to;
- a question it can answer from what the project already knows gets a short answer.

A **thread agent** owns its task. It works until the task is done, keeps a
progress checklist the user can see, replies in the thread, and asks the
coordinator (`request_coordinator`) when it needs permission or direction
beyond its scope. It resolves the thread when the work is finished.

## Runtime

Everything runs in one Cloudflare Worker (`apps/api`):

| Piece | Where | Notes |
|---|---|---|
| HTTP API | Hono, `apps/api/src/index.ts`, `routes/` | Auth, projects, membership, `GET /api/info` |
| Auth | Better Auth, `apps/api/src/auth.ts` | Cookies for the same-origin web app, bearer tokens for apps |
| Global data | D1, schema in `packages/db` | Users, sessions, projects, members, skills, connectors, usage. Each request runs on its own D1 session (`apps/api/src/d1-session.ts`), so read replication can be turned on |
| Project chat | `ProjectAgent` Durable Object | One per project; messages in its SQLite with a `seq`; WebSocket fan-out |
| Coordinator | `apps/api/src/agents/coordinator.ts` | Tools: `post_message`, `start_thread`, `message_thread`, `react` |
| Thread | `ThreadAgent` Durable Object | One per thread; keeps its state and serves Myrel's tools to the harness over MCP (`reply`, `update_plan`, `ask_decision`, `publish_artifact`, `request_coordinator`, `resolve_thread`, …) |
| Cloud harness | `Sandbox` Durable Object + Container, `apps/api/src/sandbox` | One container per thread running OpenCode. The image is built from `apps/api/sandbox/Dockerfile` and pinned by digest in `apps/api/wrangler.jsonc`, so deploys need no Docker |
| Files and artifacts | R2 (`FILES`, `ARTIFACTS`), `apps/artifacts` | Project files and artifact versions; artifacts are served from a separate origin |
| Local runner | `RunnerAgent` Durable Object, `packages/myrel-runner` | One per paired computer; holds the runner's outbound WebSocket, sends tasks, wakes the thread with each result |
| Model calls | `apps/api/src/llm` | Small provider-neutral loop; Fireworks, Anthropic, OpenAI; optional AI Gateway. Each call is metered, priced by the model that served it (`llm/pricing.ts`, `LLM_PRICES`) |
| Web app | `apps/web`, served as static assets | Vite, React 19, TanStack Router and Query, Tailwind CSS 4 |

Clients share `packages/protocol` (zod schemas for messages, threads and
WebSocket events) and `packages/client` (typed API client and a reconnecting
project socket that resyncs from the last `seq` it saw).

## Recent and coming pieces

The plan, phase by phase, is in the [README roadmap](../README.md#roadmap). The
main pieces:

- **Harnesses as thread agents (shipped).** A thread's agent is a coding
  harness, not Myrel's own loop: each turn is one run of the person's CLI on
  their computer (projects with a local folder) or of OpenCode in the thread's
  [Cloudflare Sandbox](https://developers.cloudflare.com/sandbox/). It talks to
  people through Myrel's tools over MCP (`ThreadAgent.agentMcp`), and the
  `ThreadAgent` Durable Object keeps the thread's state between turns. The
  coordinator stays a small loop in the Worker.
- **Local runner (shipped).** `myrel-runner` pairs with an account through a
  one-time code from the Devices page, then keeps an outbound WebSocket to a
  `RunnerAgent`. A project picks one of the folders shared on that computer and a
  CLI (Claude Code, Codex or Antigravity CLI), which then works that project's
  threads with the user's own login. Subscription credentials never leave the computer;
  the server stores only a hash of the runner's own token. A turn cut off by a
  runner restart (for example `myrel-runner update`) is continued automatically
  a bounded number of times (`apps/api/src/agents/auto-resume.ts`).
- **Mobile (Expo) and desktop (Tauri 2) apps** reuse `packages/client` and can
  connect to any Myrel server.

## Conventions worth knowing

- The coordinator never does the work. If you add a coordinator tool, it should
  route, not act.
- Text from outside the user (relayed messages, web pages, uploads, GitHub
  comments) is data, never instructions. Keep trust levels explicit in the
  protocol when adding new inputs.
- Each D1 schema change comes with a migration generated by `pnpm db:generate`.
  Migrations only move forward.
- In request code `env.DB` is the request's D1 session, which has `prepare` and
  `batch` but not `exec`, `dump` or `withSession`; use `env.DB_PRIMARY` for
  those. Durable Objects and the cron use the plain binding (the primary).
- After changing `apps/api/sandbox/Dockerfile`, run
  `pnpm --filter @myrel/api sandbox:image` and commit the new digest in
  `wrangler.jsonc`; otherwise containers keep the old image.
- New configuration (variable, secret, binding) is documented in
  [self-hosting.md](self-hosting.md#configuration-reference) in the same pull request.
